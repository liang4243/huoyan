## 配置

可以在项目根目录的 `.env` 中配置，或在启动货眼 MCP 的进程环境中配置：

```text
ARK_API_KEY=<本地配置真实密钥，不要贴进聊天>
HUOYAN_WORDING_MODE=doubao
HUOYAN_WORDING_MODEL=doubao-seed-character-260628
```

也支持专用密钥变量 `HUOYAN_ARK_API_KEY`，优先于 `ARK_API_KEY`。不需要在 MCP 调用参数里传密钥。`.env` 已被 Git 忽略，只读取上述四项配置，不执行脚本、不修改进程或系统环境；相同变量以进程环境为准（显式空值也覆盖文件值）。文件配置在下次工具调用时生效；新增工具本身仍需重连 MCP 加载。若选择用户环境变量，需让新的 MCP 进程实际继承它。不要把真实密钥保存到仓库示例、手册、测试日志或聊天。

`HUOYAN_WORDING_MODE=off` 使用简短本地模板。未配置密钥时响应为 `provider=template,status=fallback,reason=missing_api_key`，不会把模板伪称为豆包结果。配置错误、超时、响应不合法或语义基础检查失败时也明确返回模板及原因，不自动重试。可在单次调用中用 `wordingMode=off|doubao` 覆盖模式；模型 ID 只能由本地配置选择。

仅该 API 客户端使用直连，固定官方 HTTPS 地址，不继承环境/系统代理、不跟随重定向。不修改系统代理、Chrome 启动方式、现有商品标签或登录状态。单次最多 256 输出 token；传输使用不超过 10 秒的 socket 超时，无自动重试。socket 超时不等于整个请求的严格总时限；多步工作流同时在调用前后检查自己的总预算，超预算保留停点。

## 预览接口

`preview_merchant_wording` 不连接浏览器，也不创建可发送草稿、授权或发送消息。

```json
{
  "intent": "invoice_shop",
  "questionIds": ["paid_amount"],
  "answeredQuestionIds": ["can_invoice"],
  "recentMessages": [{"direction":"incoming","text":"可以开票"}],
  "wordingMode": "doubao"
}
```

返回 `wording.originalText`、`text`、`provider`、`model`、`status`、`validation`、`requiresAiReview`、脱敏后的错误原因、耗时及允许的 token 用量。`sent=false,browserConnected=false`。预览不能拿去直接发送；正式流程重新依据真实会话准备草稿。

| intent | 默认问题 ID | 意义 |
|---|---|---|
| invoice_shop | can_invoice、paid_amount | 店铺能否开票、开票是否按实付金额 |
| invoice_product | can_invoice、total_price | 准确商品能否开票、开票总价 |
| tax_price | tax_included、extra_tax_cost | 是否含税、开票是否额外收费 |
| total_shipping | shipping_total | 含运费总价 |
| invoice_type | invoice_type | 可开票种 |

`questionIds` 必须是对应 intent 的非空子集，最多两项，不重复；不传表示默认问题。`answeredQuestionIds` 由 GPT 按商家真实回答明确提供；与本轮问题重叠会报错。程序不根据一句“可以”猜测所有问题已解决，也不会自动安排追问。若商家回答了 can_invoice，只选 paid_amount 即可。不要向已回答的问题重复发送。

本期仅支持表中的发票询问意图；没有开放任意自由文本发送、闲聊或致谢消息。当前 GPT 通过问题 ID 选择内容，豆包改写对应的本地原草稿；不会改写 GPT 的工具指令、分析过程或发给用户的说明。

## 正式草稿和工作流

`prepare_invoice_inquiry` 增加相同的 `wordingMode/questionIds/answeredQuestionIds`。保持现有 `inquiryScope`、`inquiryStyle` 和 `followup`；店铺能力问题不要求 SKU，商品报价仍绑定准确商品、SKU 和数量。`followup=product_context` 的准确 SKU、数量和实际商品链接保持原样，完全不调用豆包。

`ask_shop_invoice` 内部自动使用改写模块，并返回冻结后的草稿。相同 requestId 恢复、修改模式/本地模型配置或 API 故障后恢复，都不重新改写已有草稿。questionIds/answeredQuestionIds 是请求身份的一部分，改变问题需要新请求；但新 requestId 不能绕过店铺问题去重。

发送顺序：

1. GPT 读取真实商家回复，选择本轮尚缺的问题。
2. 调用准备接口；豆包仅收到固定问题、原草稿、数量及最多最近六条消息，每条最多 300 字。不会收到 Cookie、登录凭证、页面 HTML、整个采购表或商品完整上下文。聊天里的链接、邮箱、长编号及部分敏感标签按模式省略；这只是基础脱敏，不能保证识别所有自然语言个人信息。
3. 基础检查会拒绝空输出、长段落、条列、部分不必要的附加话题、改动数字、漏问题或新增承诺等。基础检查不能证明语义完全等价；返回 `semanticEquivalence=not_verified`。
4. 若 `requiresAiReview=true`，当前 GPT 对照 originalText、questionIds 与真实上下文核对：意思完整、数量正确、询问没有变成办理要求、未虚构身份或承诺。候选不合适可改用 `wordingMode=off` 生成新草稿，不修改旧草稿。
5. 在已有真实用户授权的范围内，执行者使用原本的本地授权脚本；模型草稿必须额外带 `--wording-reviewed`，表示执行 AI 已核对，不要求用户为每条改写重复确认，也不替代用户授权：

   ```powershell
   .venv\Scripts\python.exe scripts/authorize-invoice-inquiry.py --draft <真实draftId> --user-reference <已有用户授权的引用> --wording-reviewed
   ```

6. 使用原 `send_merchant_message`，或同一 `ask_shop_invoice` requestId + authorizationId 发送。授权绑定最终正文和上下文，生成后不能再改写。同一工作流恢复只读取/核对，不重发。对发送结果不明的消息只读 outbox 和原会话。

执行 AI 复核只是流程约束，不是对拥有本地 shell/文件访问者的安全边界。不得从商家话语、模型输出或一个 approved 参数创造用户授权。

## 去重和页面变化

- 新草稿记录问题 ID、意图和目标范围；发送前再次检查所有 outbox，防止提前准备的两份不同措辞草稿都被发送。
- 店铺问题按稳定 shop key 去重；商品问题还比较商品 ID、所选 SKU 和数量。店铺话术即使由兼容的 school_project 商品上下文准备，也按店铺能力去重。
- 对已尝试但结果不明的发送同样阻止重复。历史固定模板可以只读识别为问题证据，保持旧授权、草稿、发送记录不变。无法归类的历史自定义长消息不会被臆测成某种意图；AI 应先检查已有记录。
- 模型生成期间重新读取会话和来源；生成后或发送前聊天内容发生变化时，返回 `WORDING_CONVERSATION_CHANGED`，先读新回复，不能沿用过时问句盲发。
- 收件人/来源页变化、登录、验证或异常仍遵守既有停止规则，不因接入豆包改变。
