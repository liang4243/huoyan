# 旺旺聊天断线恢复

2026-10-22，针对用户实际遇到两次的偶发弹窗。

## 识别范围

已在原旺旺聊天页只读确认：chat-core 内有 `role=alertdialog` 的 `.next-dialog`，标题为“连接断开”，正文“连接中断，请刷新重试”，其中有“刷新”按钮和关闭叉。

只识别此可见弹窗及准确文字，不搜索任意商家正文中的“刷新”来点击。弹窗可能在外层页或原记录的聊天 iframe；只检查这两处。模板、按钮不唯一时不猜测。截图及页面不能证明故障由代理、账号或淘宝服务端哪一方引起。

## 使用方法

优先调用 `merchant_chat_state(conversationId, tabId)`：核验原会话、合并已加载消息、对账旧 outbox，已知断线时自动执行一次恢复。`read_merchant_messages`、`wait_merchant_reply` 和准备新草稿时也支持该恢复。显式恢复接口为 `recover_merchant_chat(conversationId, tabId)`，无需重开商品或客服。

恢复动作仅点击当前已发现弹窗的“刷新”按钮，不自行构造地址或刷新其他页面。点击前保存恢复记录，刷新后最多等待8秒，核验原标签、原URL、收件人及可读取的消息。随后继续读取当前会话并核对已有发送记录，不再次发送。

等待接口和多步工作流的剩余时间预算同时约束恢复动作；剩余时间不足时返回 budget_exhausted，留待下一次读取处理，不为了恢复额外无限延长等待。

返回字段：

| 字段 | 含义 |
|---|---|
| connection.status | disconnected：已知弹窗仍在；no_disconnect_observed：未观察到此弹窗 |
| connection.transportVerified | 始终为 false；DOM 观察不能证明 WebSocket/服务端在线 |
| connection.recovery | 本轮恢复或阻止原因，如 draft_preserved、unsupported、cooldown |
| connection.lastRecovery | 最近持久恢复记录；含 actionAttempted、status、confirmed，不含新发送动作 |
| canCompose | 有可识别输入框且没有已知断线；仍需正常草稿、授权和发送前检查 |
| outbox | 原请求的发送记录；本方气泡、已读与送达证据仍分别呈现 |

`recover_merchant_chat.confirmed` 仅确认原身份可读且已知弹窗消失，不证明消息已送达。

## 保留与停止

- 编辑框中有未发送内容，或无法确定唯一空编辑框：不刷新，保留输入。
- 登录、验证码、页面异常、收件人/原URL变化：沿用原停止规则，不借恢复重试。
- 一个持续弹窗只投递一次。超时、崩溃或点击结果不明后，再调用只读核对，不因新请求ID多刷新。
- 成功后60秒内再次出现弹窗：不再自动刷新。稍后仍可检查；持续故障交给用户处理原页。
- 用户手动处理后，原会话可读且弹窗消失，后续读取可记录 cleared_without_retry；不会补发原消息。
- 发送接口本身不自动恢复重执行，发送前发现断线返回 CHAT_DISCONNECTED；改读状态后沿用原请求和既有草稿/授权。已尝试发送的请求永远只读核对。
- 只点关闭叉不能证明连接恢复，因此实现优先采用平台提供的“刷新”；不会关提示后就宣称在线。

`ask_shop_invoice` 在一次恢复仍受阻时返回 `waiting_connection`，保存原 conversationId、draftId、requestId 和 outbox，避免执行者将其理解为需重新联系商家或重新发送。

## 验收方法

`test:chat` 覆盖实际同类 DOM 的识别、原页刷新、整页/iframe 重载、原生焦点重新绑定、草稿保留、失败不重试、快速复发、身份变化、登录优先、商家正文伪装弹窗排除，以及不确定发送的只读对账。`test:research:mcp` 通过真实 MCP 传输验证恢复和重复调用不二次点击。夹具不证明所有旺旺模板兼容。

真实验收只在已记录原会话且用户允许的断线弹窗中操作，不发新消息；结果另见验收记录。
